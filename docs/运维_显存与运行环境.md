适用项目：`shitagaki-lab/see-through`（SIGGRAPH 2026，单图动漫角色图层分解）
本机：Windows 11 家庭版 / i7-13700F / 16GB RAM / RTX 3060 Ti 8GB / 驱动 610.60
最后核对：2026-11-06

---

## 1. 显存体检脚本

固定入口就是这一条，不要现场拼命令：

| 目的 | 命令 |
|---|---|
| 只看诊断（默认，绝对不改系统） | `scripts\gpu_mem.cmd` |
| 预览哪些进程会被关（仍不改动） | `scripts\gpu_mem.cmd -Clean` |
| 确认后真正清理 | `scripts\gpu_mem.cmd -Clean -Yes` |
| PowerShell 里直接调用 | `powershell -ExecutionPolicy Bypass -File scripts\gpu_mem.ps1 -Clean -Yes` |

`.cmd` 是双击入口，内部转调 `.ps1`。`.ps1` 保存为 **UTF-8 with BOM**，
这样 Windows PowerShell 5.1 和 PowerShell 7 都能正确显示中文。

### 安全边界（写死在脚本里）

- 默认只读，`-Clean` 也只读，**只有 `-Clean -Yes` 才结束进程**。
- 只精确匹配白名单进程名，最多关 10 个；未分类 / 无权限进程一律不动。
- 保护名单包括 `dwm`、`explorer`、各类 Shell 宿主、`msedgewebview2`、
  `WorkBuddy`、`powershell`、`cmd` 和安全软件进程，脚本不会碰。
- `FlClash`（代理）、`python` / `ComfyUI`（可能在跑任务）列为「谨慎」，只提示不自动关。
- 不删文件、不改注册表、不禁用设备、不停服务。

## 2. 本机显存到底被谁占了（实测）

`nvidia-smi` 在 Windows WDDM 模式下拿不到逐进程显存（显示 `N/A`），
脚本改用 Windows 性能计数器 `\GPU Process Memory(*)\Local Usage`，可以精确到 MB。

2026-11-06 采样：总计 8192 MiB，已用约 1400 MiB，空闲约 6624 MiB。

| 占用 | 进程 | 能否关闭 |
|---:|---|---|
| 227 MB | `dwm`（桌面窗口管理器） | 不能，Windows 桌面合成 |
| 166 MB | `WorkBuddy`（当前会话宿主） | 不能，正在使用 |
| 156 MB | `chrome` 主进程 | 可关，最大可回收项 |
| 129 MB | `explorer` | 不能，系统 Shell |
| 60 + 43 MB | `Weixin` ×2 | 可关 |
| 44 MB | `HipsDaemon`（安全软件） | 不能 |
| 24 MB | `csrss` | 不能 |
| 其余各 8–20 MB | 搜索/开始菜单/输入法/Edge WebView/微信小程/FDM/FlClash 等 | 部分可关 |

**结论（重要，别抱错期待）**：

- i7-13700F 是 **F 后缀、无核显**，Windows 桌面只能由 RTX 3060 Ti 渲染。
  `dwm + explorer + csrss + 一堆 Shell 宿主` 约 450–500 MB 属于**刚性占用**，清不掉。
  有核显的机器可以把显示器插主板、让核显扛桌面，这台不行。
- 全部关掉可关项，实测大概能回收 **300–450 MB**，空闲显存从 6.6GB 到 7.0GB 左右，
  不可能回到 8GB 满额。
- 因此**别把希望全押在清理进程上**，见下一节。

另外设备管理器里有 `GameViewer Virtual Display Adapter`（虚拟显示器，远程控制用）。
不远程时可以禁用它再省一点，但会影响远程访问，脚本不代劳。

## 3. 真正决定能否跑通的是推理参数

官方数字：默认 bf16 在 1280 分辨率要 12–16GB；NF4 量化版约 8GB 峰值 @1280。
本机 8GB 卡 + 桌面占用 1.4GB，**直接跑 1280 必然 OOM**。按优先级处理：

1. 首次一律 `--resolution 1024`，还 OOM 就 768。
2. Marigold 深度分辨率用 `--resolution_depth 720`（源码参数名是这个，
   不是 `depth_resolution`）。
3. 加 `--cpu_offload` 进一步省显存（代价是明显变慢）。
4. 推理前设 `$env:PYTORCH_CUDA_ALLOC_CONF = 'expandable_segments:True'` 减少显存碎片。
5. 推理前跑 `scripts\gpu_mem.cmd -Clean -Yes`，并关掉浏览器硬件加速。

`inference_psd_quantized.py` 的默认行为有两个坑：

- `--group_offload` 默认 **True**（省显存但约慢 1.5 倍），符合本机需求，保持即可。
- `--cpu_offload` 帮助文字写 "default: on"，**源码实际是 `default=False`**，以代码为准。

量化模型用的是 HuggingFace 上的**预量化仓库**，不是运行时现场量化：
`24yearsold/seethroughv0.0.2_layerdiff3d_nf4` 和
`24yearsold/seethroughv0.0.1_marigold_nf4`。
脚本仍依赖 `bitsandbytes==0.49.2` 来加载 4bit 权重，这个包在 Windows 上是最容易装砸的一环。

16GB 内存也偏紧：`group_offload` 会把权重往 CPU 内存搬，采样时物理内存只剩约 4.9GB，
虽然有 32GB 页面文件兜底不会硬崩，但会大量换页、明显拖慢。推理前建议重启或关掉吃内存的程序。

## 4. 关于 ComfyUI 的 `python_embeded`：不要用

路径：`X:\ai_tool\ComfyUI_windows_portable_nvidia\ComfyUI_windows_portable\python_embeded`（4.9GB）

实测内容 vs see-through 要求：

| | ComfyUI 便携版 | see-through 要求 | 结论 |
|---|---|---|---|
| Python | 3.13.12 | 3.12 | 不匹配 |
| torch | 2.13.0+cu130 | 2.8.0+cu128 | 不匹配 |
| transformers | 5.15.0 | 5.0.0 | 不匹配 |
| diffusers | 未安装 | 0.37.0 | 缺 |
| accelerate | 未安装 | 1.13.0 | 缺 |
| bitsandbytes | 未安装 | 0.49.2 | 缺 |
| psd-tools | 未安装 | 1.14.2 | 缺 |

三重版本冲突。在这个环境里直接 `pip install -r requirements.txt` 会连带改动
torch / numpy / transformers，**大概率把 ComfyUI 弄坏**（它自己有 106GB 模型资产）。
不要原地装，也不要拿它当 see-through 的解释器。

可行的三种做法，按推荐度：

1. **独立 conda 环境（推荐）**：干净、与官方一致，互不干扰。
   `conda create -n see_through python=3.12 -y`，然后按官方顺序装
   torch cu128 → requirements.txt → requirements-inference-bnb.txt。
2. **复制一份 `python_embeded` 出来折腾**：把 4.9GB 目录拷到独立位置再降级 torch，
   省不下多少（cu128 的 torch wheel 仍要重下约 2.5GB），且嵌入式 Python 装
   `-e ./common` 这类可编辑包容易出问题。收益低，不推荐。
3. **走 ComfyUI 生态**：README 社区支持里提到 `ComfyUI-See-through`（节点式工作流 +
   浏览器导出 PSD）和 `PNGAL`（Windows 一键整合包，自带便携 Python、固定版 ComfyUI、
   see-through 和全部模型）。如果你本来就用 ComfyUI，这条最省事，
   但插件与当前 ComfyUI / torch 2.13 的兼容性需要单独验证，本文未验证。

模型缓存现状：`C:\Users\13410\.cache\huggingface\hub` 只有 464MB（与本项目无关），
`ComfyUI\models` 有 106GB 但是 ComfyUI 格式的权重，
see-through 的 4 个 HF 仓库（全精度 LayerDiff 单仓库就 10.2GB）基本都要重新下载，
合计估计 20–30GB。GitHub / HuggingFace / PyTorch cu128 源 / hf-mirror 实测都可达
（当前走本机代理 `127.0.0.1:60053`），下载时别把代理关了。

## 5. Windows 上要注意的两处差异

- README 第 4 步 `ln -sf common/assets assets` 是 Linux 命令。
  Windows 用复制代替：`Copy-Item -Recurse common\assets assets`，README 明确允许。
- 可选 annotator 层（detectron2 / SAM2 / mmcv+mmdet）在 Windows 编译很麻烦，
  本机虽有 VS2022 但 `cl.exe` 不在 PATH，且没有 gcc/g++。
  **主推理管道 `inference_psd_quantized.py` 不依赖它们，先别装**。
  核心脚本本身没有 `os.symlink` / `fcntl` / `triton` / `/tmp` 等 Linux 专属调用，
  Windows 原生可跑。

## 8. 拉取官方仓库（工作区已有本地脚本时）

工作区根目录已经有 `scripts/`、`docs/`、`.workbuddy/`，直接用 `git clone <url> .`
会因为目录非空而失败。固定做法是在现有目录里就地建仓库再取远端内容，
**不删除、不移动任何已有文件**：

```bash
cd X:/ai_tool/see-through
git init
git remote add origin https://github.com/shitagaki-lab/see-through.git
git fetch --depth 1 origin main
git checkout -b main FETCH_HEAD
```

之后 `scripts/`、`docs/` 作为未跟踪文件留在同一个仓库里，可以一起提交。
注意：项目要求**所有脚本都必须从仓库根目录作为工作目录运行**，封装脚本内部会处理这件事。

## 10. 日常推理：input 图片 → out .psd（纯命令行，无 webui）

固定一条命令，两个位置参数：

```
scripts\infer_psd.cmd "D:\img\character.png" "D:\out\character.psd"
```

也支持命名参数：`-InputImage <路径> -OutputPsd <路径>`。

可选开关：

| 开关 | 默认 | 说明 |
|---|---|---|
| `-Resolution <int>` | 1024 | LayerDiff 分辨率，OOM 就降 768 |
| `-DepthResolution <int>` | 720 | Marigold 深度分辨率 |
| `-CpuOffload` | 关 | 再省显存，明显变慢 |
| `-SkipVramCheck` | 关 | 跳过推理前的显存体检 |
| `-CleanOutput` | 关 | 跑完删除本次中间产物（**默认保留**，便于检查分层 PNG） |

脚本做的事：校验输入与环境 → 只读显存体检 → 切到仓库根 →
用独立环境的 `python.exe` 跑 `inference_psd_quantized.py` →
定位本次生成的 `.psd` → 复制到指定的 `-OutputPsd` →
打印耗时、文件大小与 `stats.json` 里的峰值显存。

**源码里的产物路径坑**（写封装时核对过完整调用链）：

- `inference_psd_quantized.py`：`save_dir = args.save_dir`，`saved = save_dir/<图片名>`，
  并把 `saved` 传给 `further_extr(saved, ...)`。
- `common/utils/inference_utils.py` 的 `further_extr()` 内部又拼了一层
  `saved = srcd/optimized`，然后 `save_dir = dirname(saved)`，
  `psd_savep = join(dirname(save_dir), basename(save_dir) + '.psd')`。

抵消下来，**PSD 落在 `--save_dir` 内部**，文件名是 `<图片名>.psd`。
用默认 `--save_dir workspace/layerdiff_output` 时产物是
`workspace/layerdiff_output/<图片名>.psd`（不是父目录、也不是 `layerdiff_output.psd`），
同名图片重跑会覆盖。

封装脚本因此给每次推理一个独立的 `workspace/runs/<图片名>_<时间戳>`，
主产物 `workspace/runs/<tag>/<图片名>.psd`，同目录还有 `_depth.psd` 和 `.psd.json`，
中间 PNG、深度图、`stats.json` 留在 `workspace/runs/<tag>/<图片名>/` 下。
脚本找到主 PSD 后复制到你给的目标路径，并自动读取 `stats.json` 打印峰值显存。

**不启动任何 webui / Gradio / ComfyUI 界面**，纯 CLI 批处理，适合脚本串联和批量跑图。
批量处理就写个循环调 `infer_psd.cmd`，一张一张来，别并发（8GB 卡并发必 OOM）。

## 11. 极简显存模式（可选）

`explorer` 可以临时结束，桌面和任务栏会消失，但已开程序不受影响：

| 目的 | 命令 |
|---|---|
| 关 explorer + 普通应用 | `scripts\gpu_mem.cmd -Clean -Yes -Deep` |
| 恢复桌面/任务栏 | `scripts\gpu_mem.cmd -RestoreExplorer` |
| 只预览不执行 | `scripts\gpu_mem.cmd -Clean -Deep` |

`dwm` 无法关闭，`WorkBuddy` 需要**手动退出**（脚本不代劳，否则会中断当前会话）。
三者全清后大约能回收 470MB，空闲显存约 7.0GB。
极简模式请在**独立的 cmd 窗口**里执行，别在 WorkBuddy 会话内跑。
推理跑完记得 `-RestoreExplorer` 把桌面找回来。
